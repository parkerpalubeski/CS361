# Normally only public/external interfaces are documented, but that's not a hard-and-fast rule. When might you want to document internal interfaces?
* An internal interface might receive its own design document describing the internal mechanisms, and be given only to developers/AI that are assigned to work on that interface. To developers outside of that sphere, it's better to abstract it as simply "something that does this".

# Brainstorm three advantages to writing your interface and type definitions in pseudocode as opposed to real code.
* It lets you focus on the architectural structure of the interface and what it actually does, rather than syntax.
* Any developer could read the pseudocode, including those working with differing programming languages. Writing it up in something like Python instead means they actually have to interpret it in Python. This also means that if, down the line, the team wants to refactor something into another language, it is far simpler to do it since its structure is defined in something more easily translated to the new language.
* Refactoring the code if you need to make core architectural changes (as opposed to just the language) can be time consuming in an actual programming language, and especially one that is syntax-heavy like C++. In pseudocode, it would be far simpler.

# Why might a strong interface definition be more important when using AI?
* Interfaces include a great deal of ambiguity when you base its definition solely on purpose and intent. There are many ways to achieve the same goal, and an AI might give you one that you don't want, or perhaps even a frankenstein of multiple different ways to do something. If you define the structure of an API clearly, it prevents the AI from drifting off task.

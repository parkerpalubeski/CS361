# A vendor releases v2 of their API and renames several fields. Explain how wrapping the API affects the cost of adapting to this change.
Since we only have to change the calls in the place of the wrapper, the costs are significantly reduced for adaptation.

# Why does wrapping an external API make unit testing easier? Name at least two specific problems it helps you avoid.
There are no real network calls required since the API is in the program itself virtually. It makes edge case testing easier, since it gives you control over the "server". What if I wanted to test a program's response to a rate limiting? If I did that to a live server, I'd probably get blocked or even removed from the service. Simulating that virtually instead is far superior.

# Explain what an anti-corruption layer is and why a vendor's data model might be a problem if it spreads through your codebase.
ACLs ensure that data is kept intact through API services and ensures that your data model is kept independent from the vendor.

If a vendor's data model spread through a codebase, it could tie your codebase to theirs, creating significant constraints. It also means that any changes they make might completely break things unintentionally.

# A teammate proposes wrapping a small, stable API that is called from exactly one place in your code. Under what reasoning might you push back, and what conditions would change your mind?
I might push back against wrapping because it might be redundant if its only in one place anyways. It also bloats the code for no reason.

However, I might change my mind if the API is one that changes frequently. It also might just be better for consistency (all APIs wrapped) to prevent confusion, and that way someone could see it and instantly recognize it as an API since they recognize the structure of the wrapping.

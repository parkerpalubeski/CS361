# How does a Technical Design Document differ from a Functional Spec? Who (or what) is the intended consumer of each?
A technical design doc is a document for developers as well as developer tools like LLMs. The design doc says a lot more about *how* something is done than the functional spec does (specific frameworks, compatibilities, etc.)

# Why is a good Design Doc even more critical in the age of LLMs?
Design docs are essential for LLMs to aid in building what it is you actually want. It allows them to have a full-codebase context without bloating their context windows, which can help significantly with parts where that is necessary like API integration.

# Explain the difference between a constraint and a design decision.
A constraint is something that cannot be violated, either because the client has said so or because it is strictly necessary for the implementation. A design decision is something that is chosen based on what is preferred or considered best, but not explicitly necessary.

# "Each store delivers within a fixed radius (about 5 miles)." Is this more of a constraint or an assumption? Why?
This is kind of both, but better fits an assumption since the radius is approximately described "about", and its a business policy that is probably flexible and may change in the future. 

# Why would we create additional component diagrams that "drill down" into a single box? What does that gain us?
Component diagrams allow us to better understand complex parts of the program. It simplifies the implementation process into simply "connecting" parts.

# Explain why redundancy and conflicting requirements are especially risky when an LLM is a reader of the document.
When an LLM is reading a design document, it might cause context window bloat (duplicate instructions, reasoning to understand something). It also might cause hallucinations. If an LLM is given conflicting information, something that could be especially damaging is that rather than asking the human to resolve the conflict, it might probabilistically come up with a solution and ruin the program.
